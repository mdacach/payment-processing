# Plan: export Hegel-generated event sequences to CSV

Status: Implemented

## Goal

Produce a small, reproducible collection of CSV files containing ordered events generated by the existing state-machine rules. Profiles should vary event mix, sequence length, amount range, and client count without creating a file for every combination.

Each CSV has exactly this header, with no spaces in field names:

```csv
type,client,tx,amount
deposit,1,1,1.0000
withdrawal,1,2,0.5000
dispute,1,1,
```

`tx` is the new transaction ID for deposits and withdrawals and the referred transaction ID for disputes, resolves, and chargebacks. The latter three have an empty `amount`. Format amounts with `format!("{amount:.4}")`, as the binary already does for account balances; never convert through floating point. Preserve rule execution order and include events rejected by `PaymentProcessor::on_event`: the file represents inputs sent to the processor, not only successful state changes.

## Existing CSV code to reuse

- `csv = "1"` is already a normal dependency in `Cargo.toml`; do not add it again as a dev dependency. The binary already uses `csv::Writer::write_record` and `flush`, so use the same crate and writing pattern for event CSV.
- `src/main.rs` already reads the exact `type,client,tx,amount` header, trims surrounding whitespace, and maps all five CSV type names to `Event`. Its `parse_amount` helper parses decimal text, truncating fractional digits beyond four, without passing through a float. That reader is the compatibility target for generated files.
- The binary's writer produces **account balances** (`client,available,held,total,locked`), not input events. Its row mapping cannot be reused for event export. `parse_event` and `parse_amount` are private to `main.rs`; the exporter cannot call them directly from the property-test module.
- `tests/csv_cli.rs` already runs the binary with temporary CSV input and checks rejected-event handling. Extend this existing integration coverage with a generated-file compatibility check instead of creating another command-line parser test suite. `samples/transactions.csv` is a useful five-row reference, but is hand-authored rather than generated.

Extract the transaction CSV header, reader, and event-row mapping into a small shared `src/event_csv.rs` module exposed through the library. Make the binary call that reader, preserving its path/record diagnostics and its current truncation policy. Add a writer in the same module that accepts ordered `Event`s and emits canonical four-place amounts and blank amounts for non-amount events. Keep the account-balance writer in `main.rs` because it has a different schema. This gives the CLI and generator one place to maintain the transaction CSV contract.

## Recommended shape

Keep one state-machine implementation as the source of events. Add a trace to `PaymentModel` and a single `apply_event` helper that appends the event before calling `on_event`; all six rules call it (including both dispute rules). A dedicated export entry point runs one configured Hegel case, then writes the trace. Do not write CSV inside a rule or during the 5,000-case property test: Hegel can replay and shrink cases, so rule-level file writes would mix or overwrite attempts.

Start the exporter as a dedicated ignored test in `src/payment_processor/property_tests.rs`, invoked with a profile name and output path supplied by environment variables. This keeps `hegeltest` a dev dependency and permits reuse of private model state and invariants. If exporting becomes a regular user-facing command, move the shared generator into an appropriate library/tool crate and add a small CLI then; avoid duplicating the rules in an example.

`Machine::run` consumes the model and returns `()`. Give the model a shared trace handle and retain a handle in the export test to read after the run. Create a fresh trace and model for each output file. Only write the CSV after a completed case; an invariant panic must not leave a seemingly complete fixture.

## Profiles and initial files

Define profiles in code as data: permitted rules, relative weights, maximum step count, client ID range, deposit/withdrawal amount ranges in four-decimal mantissa units, and required output checks. Keep the current property-test configuration as its own default. Hegel's `#[rule(weight = ...)]` values are static, so implement configurable rule registration with `hegel::stateful::StateMachine` and `Rule::new`, delegating to the existing rule methods. Register only the rules enabled for a profile; avoid using failed assumptions to simulate disabled rules.

Suggested first collection (numbers are starting values, to tune after inspecting output):

| File | Intended coverage | Length band | Clients | Rule mix / values |
| --- | --- | ---: | ---: | --- |
| `small-deposits.csv` | Simple transactions | 10–30 | 1 | Deposits only; ordinary amounts |
| `mixed-short.csv` | Basic interleaving | 20–50 | 2–3 | Deposits and withdrawals |
| `withdrawal-heavy.csv` | Insufficient funds and successful withdrawals | 50–100 | 2–3 | Deposits retained to fund some withdrawals; withdrawal rule weighted higher |
| `dispute-lifecycle.csv` | References and account locking | 50–100 | 2–3 | All five event types, with elevated dispute/resolve/chargeback weights |
| `tiny-amounts.csv` | Four-place precision | 30–60 | 2 | Amounts concentrated near `0.0001` |
| `many-clients-long.csv` | Longer cross-client history | 500–1,000 | up to 10 | Mixed rules and broad amounts |

These are profiles, not a Cartesian product. A client range is an upper bound on distinct clients; validate the observed count, and add a deterministic initial deposit per client if a profile later needs an *exact* count. Likewise, rule weights are selection hints, not promises of an exact event mix. Each committed file must pass its profile's checks on actual row counts, event counts, amounts, and client IDs. If a generated candidate misses a required band, retry with a new recorded seed rather than relabeling the file.

## Work phases

1. [x] **Capture the trace.** Add the shared ordered trace and `apply_event` helper. Route each rule through it. Keep recording before processor application. Reconcile the deposit/dispute pools with the processor result so they represent accepted, eligible transactions; account for pool values consumed before a rule applies. Keep deliberately invalid random disputes in the trace.
2. [x] **Share the transaction CSV codec.** Move the existing header check, `parse_event`, and `parse_amount` from `src/main.rs` into `src/event_csv.rs`, then call the shared reader from the binary. Preserve trimming, extra-precision truncation, record-number errors, and parse-before-processing behavior. Add a writer in that module using the existing `csv` dependency. Map every `Event` variant to the four input fields, write the header once and rows in order, format amounts with `{:.4}`, and propagate I/O errors. Leave the different account-output writer in `main.rs`.
3. [x] **Make generation configurable.** Add a `Profile` type and named profiles. Move rule weights and enabled-rule selection to explicit `StateMachine::rules` registration while preserving the current property-test behavior. Parameterize the current hard-coded client and mantissa bounds through the profile. Keep valid references drawn from the existing Hegel pools.
4. [x] **Add the export entry point.** Add a dedicated ignored Hegel test that selects one profile, uses a fresh model, runs one case, validates the resulting trace, and writes to the requested path. Document one command per profile and a script to produce the whole named set. Use fixed, recorded seeds and disable example-database reuse for fixture generation so runs do not silently select stored counterexamples. Record Hegel version, seed, profile parameters, and observed row/event/client counts in a sidecar manifest; keep metadata out of the CSV schema.
5. [x] **Generate and review the initial set.** Generate the six files, inspect their counts and representative rows, and retain only profiles that add distinct coverage. Document whether these CSVs are committed fixtures or disposable generated output; for committed fixtures, the script should be able to regenerate them from the recorded manifest.

## Verification and completion criteria

- A codec check covers all five event variants, header spelling, empty amounts, referred `tx` IDs, four-place decimal amounts, and row order. Reading writer output back through the shared reader must reconstruct the same events.
- Existing `tests/csv_cli.rs` checks still pass after extracting the reader from `main.rs`, including whitespace, extra-precision truncation, invalid-row diagnostics, and continued processing after a rejected event.
- A small deterministic export run produces a CSV accepted by `cargo run -- <generated-file.csv>`; its rows match the captured trace, including a rejected event. The binary writes only account CSV to standard output and logs the rejection on standard error.
- Every generated file passes its declared length, client, amount, and event-mix checks; the script reports actual counts rather than assuming weights achieved them.
- Running fixture generation twice with the recorded settings and pinned dependency versions produces byte-identical CSVs. A failed Hegel run or failed profile validation leaves no final output file (write to a temporary path, then rename after validation).
- Existing regression tests and the current property test still pass. Run the long 5,000-case property test once after the refactor; use smaller focused checks during the intermediate phases.

## Decisions to settle during implementation

- For each profile, specify whether rejected events are merely retained or must occur at least once. The default is to retain all generated inputs and require rejection only in a profile named for that behavior.
- Decide whether the initial CSVs are versioned fixtures. The plan assumes the six named files are committed, with additional ad hoc exports ignored by Git.
- Keep the CSV format stable if a replay reader is added later. In particular, `tx` has the dual meaning documented above and blank `amount` means “not applicable,” not zero.
